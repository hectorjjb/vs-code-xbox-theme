## Ways to contribute

- **Report a coloring bug** — a UI element that's unstyled or hard to read.
  Open an issue with a screenshot and your VS Code version. The
  [bug report template](.github/ISSUE_TEMPLATE/bug_report.yml) prompts for what's
  needed.
- **Suggest an enhancement** — see the
  [enhancement template](.github/ISSUE_TEMPLATE/enhancement.yml).
- **Submit a fix or improvement** — follow the workflow below.

If you find a UI element that isn't colored well (or at all), the most useful
report includes a screenshot, the VS Code version, and which theme variant is
active.

---

## Prerequisites

- **Node.js 24** (CI uses Node 24). Any recent LTS ≥ 20 will build, but match CI
  when in doubt.
- **VS Code 1.90.0 or newer** (the extension's minimum `engines.vscode`).
- **`unzip`** on your `PATH` — only needed if you re-vendor the file icons
  (`npm run build:icons`).
- No global tooling required; `vsce`/`ovsx` come from `devDependencies`.

## Getting started

```bash
git clone https://github.com/hectorjjb/vs-code-xbox-theme.git
cd vs-code-xbox-theme
npm ci          # install exact, locked dependencies
npm test        # build themes from src/ and validate the output
```

### Run the themes live

1. Open the repo folder in VS Code.
2. Press **F5** (uses `.vscode/launch.json`) to launch an
   **Extension Development Host** window with the theme loaded.
3. In that window:
   - **Color theme:** `⌘⇧P` / `Ctrl+Shift+P` → **Preferences: Color Theme** →
     pick an XBOX variant.
   - **File icon theme:** **Preferences: File Icon Theme** →
     **XBOX Icons Colorful** or **XBOX Icons Green**.
4. Edit a source file under `src/`, run `npm run build`, then reload the dev host
   window (`⌘R` / `Ctrl+R`) to see your changes.

> Color and file icon themes are **independent selections** in VS Code — picking
> a color theme does not change the file icons, and vice versa.

## Project layout

```
src/                      # SOURCE OF TRUTH — edit these
  palette.json            # named color roles per variant (bg, fg, green, …)
  semantic.json           # shared semanticTokenColors (uses $role tokens)
  themes/<key>.json       # per-variant source (colors + tokenColors, $role tokens)
themes/                   # GENERATED color themes that ship in the .vsix — do NOT hand-edit
fileicons/                # File icon themes (vendored SVGs + mapping JSON)
  icons/colorful/         #   upstream full-color SVGs (vscode-icons)
  icons/green/            #   derived Xbox-green duotone SVGs
  xbox-icon-theme-colorful.json
  xbox-icon-theme-green.json
scripts/                  # build + tooling (Node ESM, zero runtime deps)
  variants.mjs            #   single source of truth for the 6 variants
  build-themes.mjs        #   src/ -> themes/
  build-icon-theme.mjs    #   re-vendor + greenify the file icons
  icon-green.mjs          #   shared green-duotone recolor helper
  screenshots.mjs         #   deterministic README screenshots -> images/
  validate-themes.mjs     #   strict checks on the built output
images/                   # committed README assets (generated by screenshots.mjs)
samples/                  # sample code used only for screenshots (not shipped)
docs/MODERNIZATION.md     # remaining/outstanding work only
```

**Key rule:** never edit files in `themes/` by hand. They are compiled from
`src/`. CI fails if the committed `themes/` don't match a fresh `npm run build`.

## How the build works

`npm run build` runs `scripts/build-themes.mjs`, which compiles each variant
listed in `scripts/variants.mjs`:

```
src/palette.json  +  src/semantic.json  +  src/themes/<key>.json
        │
        ▼  (substitute $role tokens with palette[variant][role])
themes/xbox-<variant>.color-theme.json     ← ships in the .vsix
```

- **Token substitution:** any string value of the exact form `"$roleName"` is
  replaced with that role's value for the current variant. Literal hex values
  (e.g. `"#000000"`) pass through unchanged. An **unknown `$role` is a build
  error** — this is intentional and catches typos.
- **`extends`:** a source file may set `"extends": "<key>"` to inherit another
  variant's structure and palette. `ogXbox` and `hcDark` extend `one`; `hcLight`
  extends `xbox360`. An extending theme reuses the base palette unless it
  defines its own block in `palette.json`.

Because both the build script and the validator read `variants.mjs`, they can
never drift out of sync.

## Editing a color theme

1. **Prefer palette roles over literal hex.** If you're nudging a brand color,
   change the role value in `src/palette.json` so every key that references it
   stays consistent. Reach for a literal hex only for a genuinely one-off value.
2. Edit the relevant key in `src/themes/<key>.json` (or `src/semantic.json` for
   semantic tokens). Use a `$role` token where one fits.
3. Run `npm run build` to regenerate `themes/`.
4. Run `npm run validate` (or `npm test` to do both).
5. Reload the F5 dev host and confirm the change looks right in **dark, light,
   and high-contrast** variants if your change touches a shared role.

The six variants and their outputs (from `scripts/variants.mjs`):

| Source key | Built file | Notes |
|---|---|---|
| `one` | `themes/xbox-one.color-theme.json` | dark, base for others |
| `xbox360` | `themes/xbox-360.color-theme.json` | light |
| `seriesX` | `themes/xbox-series-x.color-theme.json` | dark, extends `one`-style |
| `ogXbox` | `themes/xbox-original.color-theme.json` | dark, `extends: one` |
| `hcDark` | `themes/xbox-hc-dark.color-theme.json` | high contrast, `extends: one` |
| `hcLight` | `themes/xbox-hc-light.color-theme.json` | high contrast, `extends: xbox360` |

> **High Contrast themes:** preserve maximum contrast. Don't replace pure
> black/white focus and border colors with brand tints unless you've verified
> the contrast ratio still meets the HC bar.

## Adding a new color theme

1. Add **one** entry to `scripts/variants.mjs` (`{ key, out }`).
2. Create `src/themes/<key>.json` (optionally with `"extends": "<base>"`).
3. Add a `<key>` block to `src/palette.json` if it needs its own colors
   (an extending theme can reuse the base palette).
4. Register it under `contributes.themes` in `package.json` — **use 4-space
   indentation** to match the file (programmatic edits should use
   `JSON.stringify(obj, null, 4)`).
5. `npm test`, then F5 to verify.

## Editing the file icon themes

The file icons are **vendored** from the MIT-licensed
[vscode-icons](https://github.com/vscode-icons/vscode-icons) project — they are
not authored here. Two themes are produced from one vendored set:

- **XBOX Icons Colorful** — the upstream full-color SVGs (`fileicons/icons/colorful/`).
- **XBOX Icons Green** — a deterministic Xbox-green duotone recolor
  (`fileicons/icons/green/`, via `scripts/icon-green.mjs`).

To re-vendor (e.g. bump the upstream version), with `unzip` available:

```bash
npm run build:icons            # uses the pinned upstream version
node scripts/build-icon-theme.mjs 12.19.0   # or vendor a specific version
```

This downloads the vscode-icons `.vsix`, extracts it, rebuilds
`fileicons/icons/colorful/`, regenerates both theme JSONs, and greenifies the
green set. **After changing the version, update the "Vendored version" line in
[THIRD-PARTY-NOTICES.md](THIRD-PARTY-NOTICES.md) to match.** Then run
`npm run validate` to confirm every `iconPath` resolves.

## Regenerating screenshots

README images live in `images/` and are produced **deterministically** by a
headless Playwright + Shiki mock (not a real VS Code capture):

```bash
npm run screenshots
```

Outputs per-variant workbench mocks, palette sheets, and the
default/colorful/green file-tree panels into `images/`. Regenerate and commit
these whenever a palette or icon change would alter them. (The `previews/`
folder is local gitignored scratch and is never committed or shipped.)

## Testing and validation

```bash
npm test          # = npm run build && npm run validate
```

`npm run validate` (`scripts/validate-themes.mjs`, zero dependencies) checks:

1. Strict `JSON.parse` of every built theme (catches trailing commas, etc.).
2. Well-formed structure (`$schema`, valid `type`, `colors`, `tokenColors`,
   `semanticTokenColors`).
3. All hex color values are valid (`#rgb`, `#rrggbb`, `#rrggbbaa`).
4. Dark/light `colors` key parity.
5. No duplicate `tokenColors` scopes.
6. Each file icon theme parses, every `iconPath` resolves to a real SVG, and
   every icon reference points at a defined `iconDefinition`.

### CI

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on every push to
`main` and on every pull request:

1. `npm ci`
2. `npm run build`
3. `npm run validate`
4. **Verify built themes match committed output** — `git diff --quiet -- themes/`.
   If you edited `src/` but forgot to run `npm run build` and commit the result,
   this step fails.
5. Dry-pack with `vsce ls`.

**Before opening a PR, run `npm test` locally and commit any regenerated files
under `themes/`** so CI stays green.

## Coding conventions

- **Tabs** for indentation in `src/themes/*.json`, `src/*.json`, and `scripts/*.mjs`
  (match the surrounding file).
- **`package.json` uses 4-space indentation** — preserve it; for programmatic
  edits use `JSON.stringify(value, null, 4)` to keep diffs minimal.
- **Never hand-edit `themes/`** — change `src/` and rebuild.
- **Prefer `$role` palette tokens** over literal hex in theme sources.
- Scripts are **Node ESM (`.mjs`) with zero runtime dependencies** — keep the
  validator and build scripts dependency-free.
- Keep comments minimal and only where they clarify non-obvious intent.

## Commit and pull request guidelines

- Branch off `main` and open your PR against `main`.
- Keep PRs focused; describe the user-visible effect and attach before/after
  screenshots for any visual change.
- Include regenerated `themes/` (and `images/` if applicable) in the same PR.
- Ensure `npm test` passes locally and CI is green.
- For a user-facing change, add an entry to
  [CHANGELOG.md](CHANGELOG.md) under a new version heading
  ([Keep a Changelog](https://keepachangelog.com/) format).
- By submitting a PR you agree your contribution is licensed under the project's
  [Apache-2.0](LICENSE) license.

## Release process (maintainers)

Releases are currently manual. With a clean, tested working tree on `main`:

```bash
# 1. Bump the version in package.json and add a CHANGELOG entry, then:
npm test                       # prepublishOnly also runs this
git commit -am "…(vX.Y.Z)"
git tag vX.Y.Z
git push origin main && git push origin vX.Y.Z

# 2. Publish
npm run package                # creates the .vsix (optional sanity pack)
npm run publish:vsce           # VS Code Marketplace (needs VSCE_PAT)
npm run publish:ovsx           # Open VSX (needs OVSX_PAT)
```

`prepublishOnly` runs `npm test`, so a publish can't ship un-built themes.
See [docs/MODERNIZATION.md](docs/MODERNIZATION.md) for the planned
`release.yml` automation and remaining roadmap items.
